# Security and privacy

The backend is owner scoped and stateless. BCrypt hashes passwords; SHA-256 stores random, high-entropy bearer credentials. User tokens expire after 12 hours; logout revokes the current token. Rotating a device token invalidates its prior token. Device credentials are scoped to their own device; user credentials are required for registry operations, configuration mutation and alert acknowledgement. Unknown records are not disclosed across owners.

Telemetry and location are sensitive. Never log request bodies, tokens, passwords, raw BLE records or database secrets. The console appender has an INFO threshold even when inherited environment variables enable framework debug logging. DTO string representations redact sensitive content. Exceptions returned to clients use structured problem documents and omit SQL/stack traces.

Default HTTP binding is loopback. The development simulator server uses 127.0.0.1:8087 and explicitly enables simulator ingestion. The isolated MySQL instance binds 127.0.0.1:3317. The demo script generates unique credentials and stores them only in Git-ignored, owner-restricted files. These are development conveniences; they are not a deployment secret manager. An account/token is not allowed to claim physical hardware verification merely by choosing HARDWARE provenance; device credentials authenticate the sender, not the sensor's truthfulness.

For a LAN bench, bind only the intended interface and use a controlled network. HTTP exposes bearer tokens and measurements to the network and provides no server authentication. Production must terminate TLS with a valid certificate, use authenticated TLS to a remote database, restrict firewall access, apply login/registration rate limits at a reverse proxy, and monitor authentication abuse. Do not expose the development endpoint to the Internet. No production hardening, penetration test, certificate lifecycle or hosted deployment has been claimed.

Firmware HTTPS verifies the provisioned CA. There is no insecure TLS fallback. Firmware NVS currently stores credentials without flash encryption; enable and provision ESP32 flash/NVS encryption and secure boot through a reviewed manufacturing process for a deployed product. Serial provisioning requires physical access and is not echoed. BLE measurements/configuration require authenticated encrypted pairing. The identity characteristic is intentionally public. Pairing/bond behavior still requires physical validation.

Desktop tokens and passwords remain in process memory. Only backend address, chosen device and display timezone are saved in Java Preferences. Android encrypts credentials and JSON cache payloads with an app-scoped AES-GCM Android Keystore key; Room indexes retain device ID, receipt time and sync/review flags in the private application sandbox. Backup and device transfer are excluded. Clearing the cache also removes unsynchronized readings. Default local cache retention is seven days/10,000 samples; backend retention is configurable, default 30 days, enforced hourly. Exports contain sensitive data and are written only after a user chooses a destination.

Release Android builds disallow cleartext traffic and require an HTTPS backend address. A signed release requires private external keystore environment variables. No keystore, production credentials or production user data belong in Git. Windows artifacts need organizational code signing before public distribution; debug APKs and unsigned installers are development artifacts.

Outstanding product work includes account recovery, email verification, organization-wide access management, audit trails, account/data deletion, key recovery and rotation for encrypted Android data, medical/regulatory evaluation if applicable, and a deployment threat review. These are documented limitations, not hidden controls.
